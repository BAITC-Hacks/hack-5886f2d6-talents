# Передача «Что проверить дальше» — часть Армана

Контракт из пункта 2 [FINISH_PLAN.md](../FINISH_PLAN.md) реализован в Python
и JSON Schema. Источник подсказок — C++; Арман их не генерирует по повторным правилам.
Состояние базового ядра `9e5eff6`: версия 1.1.0 ещё не возвращает это поле.
Интерфейс этой версии загружает расширенный JSON, но пока не отображает действия.

## Формат, готовый для Артура и Савелия

В объект результата для каждого `gid` можно добавить `next_actions: string[]`.
Тот же объектный ключ по тому же gid сохраняется в `graph.json.nodes`.
Версия схемы остаётся `1.0`. Поле необязательно, `[]` допустим; строки должны быть
непустыми, а `null` и другие типы отклоняются. Текст и порядок сохраняются дословно.
Ограничений на количество действий и длину строки контракт не добавляет.
Колонки CSV и поля `top_nodes` остаются прежними.

Пример **фрагмента** объекта узла, синтетический gid (не отдельный result.json):

```json
{
  "gid": "100000000000000003",
  "next_actions": [
    "Запросить продолжение исходящих переводов за границей depth=4.",
    "Проверить источники наблюдаемых поступлений."
  ]
}
```

Это пример обмена, не результат действующего C++ 1.1.0 и не утверждение о клиенте.
Отсутствующее поле остаётся отсутствующим: Python не подставляет фиктивные действия.

## Артуру

Добавь поле в `result.nodes` по условиям из FINISH_PLAN. Совмещай ограничения
seed/depth/изоляции с ролью и зафиксируй порядок в документации ядра. Избегай
специальных gid и утверждений о виновности. Обнови engine_version и тесты правил.
Изменять CLI, обязательные поля или три CSV для этой функции не требуется.

После коммита ядра совместный прогон:

```powershell
cmake --build engine/build --config Release --parallel 2
python prepare_ui_data.py
python verify_outputs.py --data "TechTask/data(1)/data" --core engine/build/engine.exe
```

Для Visual Studio путь бинарника — `engine/build/Release/engine.exe`.
`prepare_ui_data.py` находит оба варианта автоматически. Публиковать весь
`frontend/public/data` одним комплектом вместе с новым manifest.

## Савелию

В `frontend/src/data.ts` принять необязательное поле в Client/parseGraph,
в карточке вывести список «Что проверить дальше» в исходном порядке.
Старые файлы и `[]` должны открываться без пустого блока. Получать поле из
`graph.nodes` по gid, не из top_nodes и не из CSV. Отсутствие действий не трактовать
как отсутствие риска. Проверить четыре контрольных случая и сочетания ограничений
после появления нового C++ и пересчёта данных.

## Что проверено в интеграции

- Старые результаты без поля и пустой список принимаются.
- Русский текст, порядок и наличие поля сохраняются через валидацию и экспорт.
- Неверные типы и пустые строки отклоняются в production и явном demo-режиме.
- Проверка комплекта обнаруживает потерю, изменение, перестановку и появление
  действий без источника в result.json, даже при правильных хэшах.
- Тест внешнего core worker проверяет поле на фикстуре; это не проверка новых
  правил Артура. Байты трёх CSV и ранжирование от добавления поля не меняются.

Готовность четырёх реальных сценариев с подсказками подтверждается только после
реализации C++ и показа UI. Текущий полный пересчёт проверяет совместимость
существующего ядра; синтетические подсказки в сдаваемый набор не подмешиваются.

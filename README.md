# HackAlem — данные и интеграция

Пайплайн Армана на основе организаторского `starter.py`: проверка трёх Parquet, полный направленный граф, базовые метрики, Louvain, вызов внешнего ядра, три CSV и `graph.json`. Работает локально на CPU.

**Статус интеграции:** контракт v1 и маленькие синтетические примеры готовы. C++-ядро Артура отсутствовало в исходном репозитории; его реальные роли и запуск ещё не проверены. Для независимой разработки есть явно обозначенное Python demo-ядро. Подтверждение контракта Артуром и Савелием пока не получено. UI разрабатывает Савелий.

## Передать команде в первую очередь

- Артуру: [CONTRACT.md](CONTRACT.md), [examples/input.json](examples/input.json), [examples/result.json](examples/result.json). Его CLI: `core --input input.json --output result.json`.
- Савелию: [examples/graph.json](examples/graph.json). Узлы и концы рёбер — строковые gid; полный граф после прогона — `out/graph.json`.
- Все схемы и ограничения — в контракте. Примеры содержат 4 узла, включая изолированный seed и узел на границе depth=4. Это иллюстрация протокола, не полный пример BFS-выборки.

## Установка

Python 3.12, зависимости фиксированы по проверенному окружению. При использовании этого каталога отдельно укажите `--data`; внутри исходного репозитория путь к данным уже настроен по умолчанию.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

На Linux/macOS активация: `source .venv/bin/activate`. Для установки пакетов потребуется доступ к PyPI или заранее подготовленные wheels. Сам пересчёт не использует сеть. Компиляция ядра выполняется заранее по инструкции Артура.

## Один запуск с C++

Из корня репозитория после получения собранного ядра:

```powershell
python pipeline.py --core .\build\core.exe --out out
```

Linux/macOS: `python pipeline.py --core ./build/core --out out`. Для другой структуры данных: `--data "путь/к/папке/с/parquet"`. Путь к исполняемому файлу и аргументы передаются отдельными элементами в subprocess, без shell.

## Полный демонстрационный прогон сейчас

```powershell
python pipeline.py --demo --out out-demo
```

Он действительно проходит через отдельный процесс, но роли рассчитывает **Python demo**, а не C++ Артура. `graph.json` и `run_manifest.json` содержат `demo: true`, `engine: python-demo-v1`. Это рабочая интеграционная база, не окончательное аналитическое ядро команды. В обычном режиме автоматического перехода на demo при ошибке C++ нет.

Только подготовка входа для Артура:

```powershell
python pipeline.py --prepare-only --out prepared
```

Получение `result.json` и итоговых выгрузок в этом режиме не выполняется. Используйте отдельный каталог `prepared`, чтобы не смешивать его с готовым прогоном.

## Что изменено относительно стартера

Сохранена структура `load → sanity_check → build_graph → basic_features`. Проверка сравнивает не только пары, но и их суммы (абсолютный допуск 0.01 KZT, rtol=0) и количества транзакций. Отклоняются неизвестные концы, повторные gid/рёбра, null/float ID, неверные типы/глубины, нулевые или отрицательные суммы, NaN/Infinity. Одинаковые строки транзакций остаются в данных: без transaction_id нельзя доказать дубликат. Период и порог из описания контролируются предупреждениями, а не подгонкой данных.

В `DiGraph` сначала добавляются **все** узлы. Степени и обороты считаются на направленном графе; PageRank — с весом `sum_kzt`, alpha=0.85, tol=1e-10, max_iter=1000. Изолированные узлы участвуют в PageRank. Неположительный знаменатель pass_through кодируется как `null`; для корректных входов это только нулевой вход. Сохранён флаг стартера `truncated_by_depth`.

Louvain выполняется на неориентированной проекции с суммой весов обоих направлений, без петель, seed=42, resolution=1.0. Узлы без рёбер проекции получают отдельный кластер. Перед расчётом данные сортируются. Направления сохраняются во всех остальных расчётах. Внутренний оборот кластера считается по исходным направленным рёбрам один раз, включая петли. Поэтому он не удваивается при построении проекции. Число кластеров не подгоняется под упомянутые в ТЗ сообщества с несколькими seed.

## Проверка ядра и ошибки

`result.json` должен содержать все и только входные gid, по одному разу, роли из словаря, конечные оценки 0–1, непустые evidence/why. Evidence — максимум 200 символов. Метка terminal для depth=4 с нулевым исходящим отклоняется. Проверка структуры — не проверка аналитической обоснованности; правила Артура нужно дополнительно обсудить.

Ошибки возвращают ненулевой exit code. Ключи JSON не должны повторяться. Новый результат создаётся в уникальном временном каталоге, поэтому старый `result.json` не может подменить ответ ядра. При ошибке до публикации старые CSV/graph остаются целыми. Публикация файлов выполняется по одному, manifest — последним; это не атомарная замена всего каталога. Потребитель может проверить хэши из manifest. Не запускайте два процесса с одним `--out` одновременно. После ошибки следует учитывать exit code, а не наличие файлов от прошлого прогона.

Общий таймаут 300 секунд включает загрузку Python-зависимостей дочернего процесса, чтение, расчёт, subprocess и экспорт; таймаут ядра по умолчанию 120 секунд. `--timeout` можно уменьшить. При превышении процесс завершается с кодом 124. Установка зависимостей и предварительная компиляция ядра в время пересчёта не входят.

## Демонстрационные правила, которые должен заменить/подтвердить Артур

Порядок правил важен: срабатывает первое подходящее. `reliable` здесь означает положительный вход, не seed, depth<4; это не гарантия полноты банковского баланса.

| Порядок | Роль | Условие | role_score |
|---|---|---|---|
| 1 | peripheral | нет рёбер либо depth=4 и нет исходящих; явно пишем «роль не установлена» | 0 |
| 2 | coordinator | in_deg>=3, out_deg>=3, прямых seed-плательщиков>=2, сообществ среди соседей>=2 | 0.55 |
| 3 | distributor | out_deg>=10 | 0.70 |
| 4 | transit | reliable, есть вход и выход, 0.8<=pass_through<=1.2 | 0.65 |
| 5 | consolidator | reliable, in_deg>=3, pass_through<0.5 | 0.70 |
| 6 | terminal | reliable, есть вход, out_deg=0 | 0.50 |
| 7 | peripheral | ни одно условие не выполнено | 0.25 |

Приоритет: `0.35*V + 0.25*P + 0.20*S + 0.20*role_score`, где `V=log1p(in_kzt+out_kzt)/max(log1p(оборот))`, `P=pagerank/max(pagerank)`, `S=min(seed_in_neighbors/3,1)`. При нулевом максимуме соответствующая компонента 0. Изолированным узлам назначается 0; на depth=4 применяется коэффициент 0.6 из-за неполноты. Это эвристика для demo; она не обучена и не калибрована. Изолированный seed с приоритетом 0 всё равно может требовать проверки по внешней информации, которой в датасете нет.

## Ограничения анализа

- Depth=4 — обрыв наблюдений; исходящие дальше неизвестны.
- Входящие seed неполны; у прочих узлов также могут отсутствовать внешние потоки. Отношение сумм не является полным балансом и не доказывает движение одних и тех же денег.
- Нет переводов ниже 5000 KZT, за другие периоды и вне банка. Нет атрибутов клиента и размеченных ролей.
- Louvain показывает сообщества переводов, не устанавливает существование преступной группы. Все роли, объяснения и гипотезы предназначены для проверки аналитиком.
- Пороговые роли демо не используют временные паттерны. Отсутствие исходящих в месячном окне не доказывает окончательное удержание.

```powershell

```

Тесты покрывают большие int64 gid, изолированные узлы, границу depth, суммы/количества, ошибочные данные и ответы ядра, суммирование встречных рёбер, петли, сортировку и состав выгрузок, subprocess и таймаут. ## Рост до миллиона узлов

NetworkX хранит тяжёлые Python-объекты; заменить граф на CSR/igraph/NetworKit либо C++ и группировать транзакции потоково PyArrow/DuckDB. Для кластеризации использовать масштабируемую реализацию Louvain/Leiden с тем же явно определённым весом. Убирать материализацию всех JSON-объектов, обмениваться Arrow/Parquet или потоковым NDJSON. UI загружает агрегаты кластеров и окрестности по запросу, а не миллион вершин сразу. Порог 5 минут на новом объёме требует отдельного замера; текущий результат его не гарантирует.

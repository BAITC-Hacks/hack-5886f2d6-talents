# Контракт аналитического ядра v1

Ответственный за ядро — Артур. Python-пайплайн Армана вызывает:

```text
engine input.json result.json
engine input.json result.json --config overrides.json
```

Начиная с версии ядра 1.1.0 также поддерживается старый вызов Python Армана:

```text
engine --input input.json --output result.json [--config overrides.json]
```

Именованные и позиционные пути не смешиваются. Канонический контракт ниже
сохраняется: переход Python на плоские метрики и позиционные аргументы совместим
с этой же программой. Детали и состояние совместного прогона —
[INTEGRATION.md](INTEGRATION.md).

JSON — UTF-8, `schema_version` — строка `"1.0"`. Все `gid`, `src`, `dst` —
строки с канонической десятичной записью int64, например `"9223372036854775807"`.
Нельзя передавать их через float. `NaN` и `Infinity` запрещены: в Python использовать
`json.dump(..., ensure_ascii=False, allow_nan=False)`, отсутствующее отношение — `None`.

Машиночитаемые схемы: [input.schema.json](schemas/input.schema.json),
[result.schema.json](schemas/result.schema.json). Дополнительно ядро проверяет
согласованность рёбер, метрик, уникальность идентификаторов и диапазон int64.

## Вход

Корневой объект: `schema_version`, `nodes` (массив), `edges` (массив).
Дополнительные поля разрешены и игнорируются.

Обязательные поля каждого узла (плоская структура, имена как в стартере):

| Поле | Тип | Значение |
|---|---|---|
| gid | string | Уникальный int64 в виде строки |
| depth | integer | 0–4 при настройках по умолчанию |
| is_seed | boolean | Исходный клиент |
| cluster_id | integer | Неотрицательный номер кластера от Python |
| in_deg, out_deg | integer | Число входящих/исходящих уникальных пар |
| in_kzt, out_kzt | number | Суммы в наблюдаемом графе, неотрицательные |
| in_tx, out_tx | integer | Число входящих/исходящих транзакций |
| pagerank | number | Конечное число в диапазоне 0–1 |

Необязательные поля: `pass_through` (число >=0 или null),
`truncated_by_depth` (boolean). Если переданы, проверяются на согласованность.
Все узлы из nodes.parquet обязательны, включая изолированные с нулевыми метриками.
Ядро не присваивает cluster_id, поэтому к моменту вызова кластеризация должна быть готова.

Адаптер совместимости 1.1.0 принимает те же базовые метрики во вложенном объекте
`metrics`, а `truncated_by_depth` — в `flags`, как в первом коммите Армана.
`gid`, `depth`, `is_seed`, `cluster_id` остаются на верхнем уровне узла.
Если поле одновременно задано плоско и во вложенном объекте, значения должны
совпадать, иначе возвращается ошибка. Другие производные поля Python (например,
`neighbor_clusters` и `pass_through_reliable`) не заменяют расчёты ядра.
JSON Schema входа описывает канонический плоский формат; вложенный формат
поддерживается только адаптером на входе. Выход для обоих вариантов одинаков.

Обязательные поля каждого ребра:

| Поле | Тип | Значение |
|---|---|---|
| src, dst | string | Идентификаторы существующих узлов |
| sum_kzt | number | Положительная агрегированная сумма |
| n_tx | integer | Положительное число транзакций |

`depth` ребра можно передавать, ядро его не использует. Одна строка на пару
src→dst; встречное ребро — другая пара. Повторы одной пары — ошибка.
Степени, суммы и числа транзакций проверяются против рёбер. Для сумм допускается
погрешность `0.01 + 1e-9 * max(abs(a), abs(b))` KZT.

## Выход

```json
{
  "schema_version": "1.0",
  "engine_version": "1.2.0",
  "engine": "money-graph-cpp/1.2.0",
  "nodes": [],
  "top_nodes": [],
  "meta": {}
}
```

`nodes` содержит ровно по одной строке на входной узел, отсортированной по числовому gid:

| Поле | Тип | Значение |
|---|---|---|
| gid | string | Исходный идентификатор |
| cluster_id | integer | Исходный номер кластера |
| role | string | consolidator / transit / distributor / terminal / coordinator / peripheral |
| role_score | number | 0–1, сила соответствия эвристике, не вероятность |
| priority_score | number | 0–1, приоритет проверки |
| evidence | string | Русское объяснение роли с числами, <=200 Unicode-символов |
| why | string | Русское объяснение приоритета с числами, <=200 символов |
| features | object | Дополнительные графовые признаки |
| role_candidates | array | Все подходящие роли со score, в порядке выбора |
| priority_breakdown | object | Четыре сигнала и их взвешенные вклады |
| warnings | array of strings | Ограничения наблюдения |
| next_actions | array of strings | Следующие действия аналитика; всегда есть в ядре >=1.2.0, необязательно для старых результатов v1 |

### Следующие действия: дополнение 1.2.0

`nodes[].next_actions` — массив **от 1 до 3 уникальных непустых строк** на русском,
каждая не длиннее 200 Unicode-символов. Это рекомендации для проверки гипотезы,
а не выполненные запросы или доказанные нарушения. Поле вычисляется из признаков
и основной роли, без специальных gid и без нового обхода графа.

Порядок фиксирован: отсутствие связей или только петли → граница обхода → seed →
действие основной роли. Все применимые ограничения накапливаются. Узлы без внешних
контрагентов получают запрос полноты вместо общего действия peripheral, поэтому
максимум равен трём. Альтернативные роли не добавляют отдельные рекомендации.
Точные условия: [README — Следующие действия](README.md#следующие-действия-аналитика).

Пример для граничного consolidator с тремя отправителями:

```json
"next_actions": [
  "Запросить продолжение исходящих переводов за границей обхода (depth=4); видимые исходящие могут быть неполными.",
  "Проверить источники поступлений от 3 отправителей и основания переводов; сопоставить даты и суммы."
]
```

`schema_version` остаётся `"1.0"`; старый результат без поля принимается схемой.
Роли, обе оценки, evidence, why, warnings, top_nodes и три обязательных CSV
не изменяются. CLI и входные поля прежние.

**Арману:** `validate_result` уже сохраняет `next_actions`, если поле присутствует;
обновлённая JSON Schema ядра проверяет тип, размер, уникальность и длины строк.
Существующее объединение узлов при экспорте сохраняет поле в graph.json.
После финального пересчёта проверить равенство списков для всех gid. Старым
результатам не приписывать вычисленные действия; отсутствие поля допустимо.

**Савелию:** читать `node.next_actions` как необязательный `string[]`, показывать
в указанном порядке в блоке «Что проверить дальше». Для старого пакета без поля
блок скрывать. Тексты приходят из C++; фронтенд их не пересчитывает.

`features`: `seed_reach_count`, `direct_seed_senders`, `min_seed_hops` (null,
если недостижим из других seed), `external_cluster_count`, `cross_cluster_edges`,
`counterparty_count`, `nonself_in_deg`, `nonself_out_deg`, `observed_in_kzt`,
`observed_out_kzt`, `observed_pass_through` (null при нулевых входящих),
`boundary_node`, `truncated_by_depth` и перцентили сумм/числа контрагентов.
Из сумм observed_* и числа контрагентов исключены переводы самому себе.

`top_nodes` — первые min(20, N) узлов, поля `rank`, `gid`, `role`,
`priority_score`, `why`. Порядок: убывание неокруглённого priority_score,
при равенстве — возрастание числового gid. Python может построить более длинный топ.

`meta` содержит количество узлов/рёбер/seed, эффективную конфигурацию и описание
ограничений. Время и случайные значения не включаются: одинаковый вход даёт одинаковый выход.
Поле `engine` — дополнительный строковый алиас для первого валидатора Python.
`engine_version` и остальные поля канонического результата сохраняются.

Python объединяет nodes результата с исходными метриками по gid (`validate="one_to_one"`),
сохраняет CSV, составляет clusters.csv и graph.json. Для CSV gid преобразуется в
целое Python напрямую из строки. Нельзя соединять строки по позиции массивов.

## Ошибки и запуск

Код выхода 0 — успех, 1 — ошибка данных/конфигурации/файлов, 2 — неверные аргументы.
Диагностика идёт в stderr. При ошибке входа/конфигурации существующий result.json
не изменяется. При ошибке записи результат может быть неполным: обязательно проверять код выхода.

```python
subprocess.run([str(engine_path), str(input_path), str(result_path)], check=True)
```

Весь JSON читается в память. Для текущих размеров это приемлемо. Установка C++
зависимостей из интернета при сборке не нужна: nlohmann/json включён в engine/third_party.

# Аналитическое ядро графа переводов

C++17-часть Артура: принимает метрики и кластеры из Python, вычисляет признаки
связей, присваивает объяснимые роли и приоритет проверки каждому узлу.
Результат — `result.json` для пайплайна Армана. Интерфейс и итоговые CSV собираются
другими частями проекта. Все выводы являются гипотезами для проверки аналитиком.

Начать интеграцию: [контракт JSON](CONTRACT.md),
[пример входа](examples/input.json), [пример результата](examples/result.json).

## Быстрый запуск

Нужны C++17-компилятор и CMake >=3.16. Зависимость nlohmann/json 3.12.0 уже
включена в репозиторий; сборка и работа ядра не требуют сети или Python.

```sh
cmake -S engine -B engine/build -DCMAKE_BUILD_TYPE=Release
cmake --build engine/build --config Release --parallel 2
./engine/build/engine engine/examples/input.json engine/test-output/example.json
```

При сборке Visual Studio программа находится в `engine/build/Release/engine.exe`.
При MinGW/Ninja — `engine/build/engine.exe`. В CLion можно открыть `engine/` как
самостоятельный CMake-проект и выбрать конфигурацию Release.

На Windows есть скрипт, который находит инструменты в PATH или установленном CLion:

```powershell
powershell -ExecutionPolicy Bypass -File engine/build.ps1
& .\engine\build\engine.exe engine/examples/input.json engine/test-output/example.json
```

Настройки по умолчанию встраиваются из `config/default.json` при сборке. Для
изменения правил без пересборки передать JSON с переопределяемыми ключами:

```sh
engine input.json result.json --config overrides.json
engine --print-config
```

В `meta.config` результата всегда сохраняются реально применённые параметры.
Неизвестные настройки, неверные типы, некорректный интервал транзита и сумма весов
приоритета, отличная от 1, приводят к ошибке.

## Метрики и неполнота наблюдений

Ядро использует входные метрики стартера. Однократная агрегация рёбер нужна для
проверки их согласованности. Переводы самому себе исключаются из признаков ролей
и приоритета; исходные метрики и данные Python не меняются.

- `I`, `O`: наблюдаемые входящие/исходящие суммы без переводов самому себе.
- `D_in`, `D_out`: число разных внешних отправителей/получателей.
- `V = max(I, O)`: показатель объёма потоков. Это не баланс и не остаток.
- `S`: число разных seed, из которых узел достижим по направлению рёбер.
  Сам узел себя не учитывает даже при возвратном цикле. Один seed учитывается один раз.
- `B`: количество отличных от собственного кластеров среди непосредственных
  контрагентов, по обоим направлениям. Встречные рёбра не удваивают число кластеров.
- `P`: число уникальных внешних контрагентов, объединение отправителей и получателей.
- `min_seed_hops`: длина кратчайшего пути из любого другого seed или null.
- `direct_seed_senders`: число непосредственных отправителей, являющихся seed.

Графовая достижимость описывает возможную структурную связь. Дат в input.json нет,
поэтому она не устанавливает хронологию переводов или происхождение конкретных денег.

Для всех узлов указано, что виден только фрагмент графа. Для seed отдельно
отмечается неполнота входящих, для depth=4 — исходящих. Даже вне границы обхода
не видны другие банки, другие месяцы и переводы ниже 5000 KZT.

## Формальные правила ролей

`Q(X)` — эмпирический перцентиль среди строго положительных значений X:
число положительных значений <= X, делённое на число положительных значений.
При X=0 или отсутствии положительных значений Q=0. Одинаковые значения имеют
одинаковый перцентиль. Перцентили считаются по всему переданному графу.

Применяются правила в следующем порядке. Первое сработавшее определяет основную
роль; все подходящие роли доступны в `role_candidates`. Выбирается наиболее
специфичное правило по этому порядку, а не наибольший score.

| Порядок | Роль | Правило по умолчанию |
|---|---|---|
| 1 | coordinator | S>=3, B>=2, D_in>=2, D_out>=2, Q(V)>=0.75 |
| 2 | consolidator | D_in>=3, D_in>D_out, I>0, Q(I)>=0.5 |
| 3 | distributor | D_out>=5, D_out>D_in, O>0, Q(O)>=0.5 |
| 4 | transit | Не seed, depth<4, D_in>0, D_out>0, I>0, 0.8<=O/I<=1.2 |
| 5 | terminal | Не seed, depth<4, D_in>0, исходящая степень включая петли = 0, I>0 |
| 6 | peripheral | Ни одно правило выше не выполнено |

`coordinator` означает кандидата на структурно связующую роль. Достижимость и
связи с сообществами сами по себе не устанавливают организатора группы.
`terminal` означает отсутствие наблюдаемых исходящих в этой выгрузке; роль не
доказывает, что средства остались на счёте. `peripheral` означает недостаток
признаков выбранных правил, а не отсутствие риска.

Граничный узел может быть consolidator при нескольких наблюдаемых отправителях.
Нулевые исходящие на границе не используются как доказательство роли terminal.
На границе также отключён transit, поскольку его отношение зависит от исходящих.

### Сила соответствия роли

Обозначим `sat(x, t) = min(1, x/t)`. Пороговые значения берутся из конфигурации.
Сначала вычисляется базовая сила:

| Роль | Формула |
|---|---|
| coordinator | 0.5 + 0.2*sat(S, 2*min_seeds) + 0.15*sat(B, 2*min_external_clusters) + 0.15*Q(V) |
| consolidator | 0.55 + 0.25*sat(D_in, 2*min_senders) + 0.2*Q(I) |
| distributor | 0.55 + 0.25*sat(D_out, 2*min_receivers) + 0.2*Q(O) |
| transit | 0.5 + 0.3*C + 0.2*min(Q(I), Q(O)) |
| terminal | min(0.8, 0.5 + 0.2*Q(I) + 0.2*sat(D_in, 3)) |
| peripheral | 0 |

В формуле transit `C = max(0, 1 - abs(O/I - 1)/W)`, где W=1-ratio_min
для O/I<1 и W=ratio_max-1 иначе. Близость к 1 показывает совпадение наблюдаемых
сумм, а не доказательство сквозного транзита.

Базовая сила умножается на 0.8 для границы обхода и на 0.85 для seed
(при обоих условиях — на оба коэффициента). Это прозрачные эвристические
коэффициенты качества наблюдений. Без ground truth статистическая калибровка
и измерение accuracy невозможны. Коэффициенты формул фиксированы в версии ядра;
пороги, множители качества и веса приоритета настраиваются JSON-файлом.

### Приоритет проверки

```text
priority = 0.35 * sat(S, 5)
         + 0.30 * Q(V)
         + 0.20 * Q(P)
         + 0.15 * sat(B, 3)
```

Приоритет оценивается отдельно от роли: пограничный сборщик может быть полезен
для проверки даже при неполной информации. Изолированные узлы имеют приоритет 0.
В `priority_breakdown` для каждой из четырёх частей сохранены signal, weight,
contribution; сумма contribution равна priority_score с погрешностью float.
Поле `why` содержит исходные числа для объяснения места в топе. Баллы не являются
вероятностью противоправной деятельности.

Результат сортируется по числовому gid. Топ сортируется по убыванию приоритета;
при равенстве — по возрастанию числового gid. Значения перед сортировкой не округляются.

## Проверки

Регрессионные тесты требуют только Python >=3.9, без сторонних пакетов:

```sh
python engine/tests/test_engine.py engine/build/engine.exe -v
```

Если CMake нашёл Python, они доступны через CTest:

```sh
ctest --test-dir engine/build -C Release --output-on-failure
```

Проверяются все шесть ролей, граница обхода, seed, циклы, изолированные вершины,
петли, int64-идентификаторы, Unicode-пути, ошибочные данные, конфигурация,
детерминизм и совпадение достижимости с независимым эталонным расчётом.

Для проверки на Parquet организаторов есть вспомогательный тестовый адаптер:

```sh
python -m venv engine/.venv
# Windows: engine/.venv/Scripts/python.exe; Linux/macOS: engine/.venv/bin/python
engine/.venv/Scripts/python.exe -m pip install -r engine/tests/requirements.txt
engine/.venv/Scripts/python.exe engine/tests/check_dataset.py engine/build/engine.exe
```

Он использует исходный starter.py, проверяет суммы и количество транзакций,
вычисляет тестовые Louvain-кластеры, вызывает C++ и сравнивает достижимость с
NetworkX. Пишет `input.json`, `result.json`, `validation.json` в `engine/test-output/`.
Это проверка C++-части и пример подготовки входа для Армана. Готовый production
пайплайн, три CSV и интерфейс принадлежат другим частям команды.

## Производительность и масштабирование

Для N узлов, M рёбер и S seed расчёт достижимости занимает O(S*(N+M)), с
дополнительной памятью O(N). Списки смежности занимают O(N+M). Проверка пар,
сортировки и перцентили требуют O(N log N + M log M); JSON целиком находится в памяти.
См. [результаты проверки](VALIDATION.md) для фактического прогона текущего датасета.

При росте до миллиона узлов потребуются потоковое чтение или бинарный формат,
CSR-представление графа и компактные массивы признаков. Для большого числа seed —
распространение битовых наборов по конденсации сильно связных компонент либо
приближённые счётчики достижимости; сложность и память зависят от числа seed.
Louvain и визуализацию следует считать/загружать по частям. Текущая версия
на таком масштабе не тестировалась.
